# 像素答题打 Boss：开发文档

版本：设计草案 v0.1。更新：2026-10-22（Asia/Shanghai）。

## 1. 项目目标与边界

做一个适合朋友聚会的移动端网页游戏：5–6 人进入同一房间，通过简单、轻松的限时答题共同击败像素 Boss；个人贡献榜提供竞争感，每局目标时长约 3–5 分钟。

初版交付一条完整可玩的流程：房主登录 → 创建房间 → 展示二维码 → 玩家扫码、填写昵称 → 房主开始 → 同题限时答题 → 战斗结算 → 排名 → 再来一局。

首版仅面向小规模使用，采用单台 VPS、单个游戏服务实例。多实例扩容、职业装备、商城、语音、永久玩家账号、微信 OAuth、AI 实时出题和复杂关卡均不列入首版。

## 2. 需求确认与设计假设

### 2.1 用户已经确认

| 项目 | 内容 |
| --- | --- |
| 场景 | 一个网页房间内约 5–6 人实时游戏 |
| 玩家网络 | 主要在中国大陆，通过扫码进入 |
| 域名 | tools.luminestella.top；用户已在 Cloudflare 添加一条 A 记录 |
| 风格 | 像素风，题目轻松、简单 |
| 核心战斗 | 答对扣 Boss 血量，答错扣自己的血量 |
| 淘汰规则 | 生命归零后本局只能旁观；存活队员继续答题，全队倒下挑战失败，下一局恢复生命 |
| 答题方式 | 全员同时答同一道题，每题限时，避免长时间等待 |
| 房主 | 有账号、可建房并生成二维码，可参与或观战，可查看房间游戏操作 |
| 排行 | 展示个人伤害、正确率等贡献信息 |
| 服务器 | 已有美国 Ubuntu VPS，安装了 1Panel，另有可连接 VPS 的国内 Windows 云服务器 |
| 源站保护 | 希望普通玩家不直接看到、连接 VPS IP |
| 部署协作 | 用户可以手动部署；如管理连接可行，也希望助手协助部署 |

### 2.2 初版建议，尚待试玩或后续确认

- 最多 6 名参战玩家，房主参战占一个席位；另允许最多 2 名观战者，避免无限占用连接。
- 扫码进入使用游客身份，不自动获取微信头像和昵称。
- 每题默认 10 秒，可在开局前选择 8 / 10 / 15 秒；结算约 2 秒。
- 题数默认 15 道；通过实际试玩调整题数和动画时间，使局长接近目标。
- 房主可以在下一题开始时切换参与/观战；中途首次加入的普通玩家先观战，下一局参战。
- 切换到观战后，局内血量和成绩仍保留；切回不会重置血量，避免用切换回血。
- 题目基础伤害 10；初始生命值 3；答错或在线超时扣 1 点生命。
- 连对 3 题，第三题额外造成 5 点伤害，之后连击重新累计；答错或超时清空连击。
- 全员答对触发一次额外团队合击，团队伤害不记入个人榜。
- 生命归零即淘汰，本局不能继续答题、伤害 Boss 或复活；仍能看题目、战场和榜单。下一题从存活参战名单中排除，答题统计停留在淘汰时。刷新或切换角色不恢复血量，下一局统一恢复 3 点生命。此规则已由用户确认。
- 结算榜优先按个人总伤害排序，其次正确率、答对题数，再以稳定加入顺序打破平局；不奖励最快抢答。
- 参战玩家刷新或重连保留身份；服务器进程重启时结束未完成对局，已落库战绩保留。首版不承诺跨进程恢复对局。

## 3. 游戏规则与节奏

### 3.1 每题流程

1. 服务端确定本题参战名单，发送题目、选项、开始时间和截止时间，不发送答案。
2. 玩家提交后锁定选项，角色显示“已就绪”；不能改答案，不能同题重复攻击。
3. 本题所有仍在线的参战者均已提交，或到达服务端截止时间时，结束作答。
4. 服务端一次性判题、结算伤害与血量、更新排行榜，发布正确答案和简短解释。
5. 播放约 2 秒攻击、受伤和合击效果，随后自动进入下一题。
6. Boss 血量降为 0 则获胜；题数耗尽或没有存活参战队员且 Boss 仍存活则失败。保留约 2 秒结算展示后进入终局，不再继续出题。

作答期间不公布其他人的具体选项、对错和攻击伤害，防止答案通过动画泄露。所有人都在第 4 秒提交时，约第 6 秒即可开始下一题。

倒计时以服务端时间为准；前端校正时差并显示进度条。截止前到达服务端的首次合法提交才有效。全员提交时进行小幅延迟的结算调度，为已排队的合法事件保留处理机会；不额外增加可作答时间。

### 3.2 Boss 数值与变动人数

原型暂设 Boss 最大血量为 `开局参战人数 × 15 × 10 × 0.65`，取整。这表示忽略技能时，约 65% 团队正确率能接近基础通关线；合击和连击会降低实际所需正确率，必须通过试玩校准。

Boss 最大血量在开局锁定，不因临时掉线或切换观战动态降低。中途掉线后仍可恢复；有人永久退出时房主可重开。首版优先保持规则可理解。

全员答对的判定使用本题开始时锁定的参战名单，且至少 2 人；掉线者不阻止提前结束，但其未提交会使本题不触发全员合击。掉线不能被用于获得更容易的合击。

已在此前题目中淘汰的人不进入本题参战名单，也不占等待人数和合击条件。倒下的房主仍保留管理权限，但不能重新切换进战斗；最后一位存活的房主不能将战场交给全部已倒下的队友后转为观战。

个人伤害记录该题生成的有效攻击值，即使最后一击溢出 Boss 剩余血量，也不按网络提交顺序截断个人贡献；Boss 实际血量最低为 0。这样同轮答对者受到公平对待。

### 3.3 掉线、暂停、角色切换

- 掉线身份和参战席位保留 60 秒；截止时未提交记一次超时，对局内统计不能通过断线逃避错误。
- 连接确认断开后，不把该连接列为“全员已提交”的等待障碍；若全部参战者离线，自动暂停，不连续消耗题目。
- 重连时发送完整快照，包括当前阶段、服务器时间、题目、自己是否已提交、血量和榜单。
- 超过保留期或首次中途加入，作为观战者进入；已离开的身份仍保留战绩，不能重建游客身份占回席位刷分。
- 房主参与/观战按钮在下一题生效；当前题按开始时身份结算。
- 房主暂时离线时，已有对局继续自动运行；无自动转移房主权限。等待房主时不能开新局。
- 手动暂停仅冻结游戏，不揭示答案；记录剩余时长，恢复时重设截止时间。暂停期间拒绝新答题请求。

## 4. 身份、房间与房主视角

### 4.1 房主账号

初版只提供一个由部署配置初始化的房主账号，不开放公众注册。登录使用服务端会话和安全 Cookie；密码保存为带盐的可靠密码哈希，不写进前端或仓库。

房主可创建房间、修改开局设置、开始、暂停、继续、锁定加入、移除玩家和再来一局。所有管理操作由服务器验证权限，不能仅靠前端隐藏按钮。

### 4.2 游客与二维码

二维码内容为同域名的 HTTPS 邀请链接，例如 `/join/<随机邀请标识>`，不含源站 IP、管理密码或房主会话。昵称、角色头像和游客身份绑定，刷新后可恢复。

邀请标识采用不可预测随机值；可另提供短房间码，但需限制尝试频率。房间关闭后邀请失效，重开同一房间可继续使用邀请，房主主动重新生成邀请时旧链接失效。

默认房间闲置 2 小时后回收，活跃对局不受闲置回收影响。容量、昵称长度和重复名处理由服务端校验。

### 4.3 房主看到什么

- 与普通玩家一致的公共战场、Boss 血量、角色动画和贡献榜。
- 玩家列表、在线状态、参战状态、已提交/思考中，以及加入、离开、角色切换、暂停等事件。
- 每题结算后查看所有玩家的具体提交、对错、伤害和受伤结果。
- 提供玩家视角切换，查看对应玩家的游戏面板；不做屏幕视频传输或鼠标轨迹采集。
- 房主参与时遵循同样的答案保密规则；默认纯观战也不提前泄露答案。如未来需要实时查看未结算选项，单独确认规则后扩展。

## 5. 页面与像素风设计

| 页面 | 主要内容 |
| --- | --- |
| 首页 | 游戏介绍、输入房间码、房主登录入口 |
| 房主登录 | 账号、密码、错误提示 |
| 房主大厅 | 创建房间、题库分类、题数、限时设置 |
| 等待房间 | 二维码、邀请链接、角色列表、参与/观战切换、开始按钮 |
| 战斗页面 | Boss 与血条、像素角色、个人生命、题目、四个大按钮、倒计时、排行榜 |
| 结算页面 | 成败、个人成绩、团队战绩、输出王/答题达人等称号、再来一局 |

手机竖屏优先。战斗区置顶、题目与选项居中、排行榜折叠或置于下方，避免六人榜单挤压答题按钮。房主桌面端可同时显示战场与事件面板。

像素风用于角色、Boss、边框、背景和动效；中文题目与选项采用清晰易读字体。提供静音、减少动画开关，颜色之外用文字/图标区分正确与错误。首次用户交互后再启用声音。

首版 1 个 Boss、少量玩家头像、攻击和受伤动画。素材需自制或来源许可明确。初步效果可用 CSS / SVG 与少量精灵素材完成，不强制引入大型游戏引擎。

## 6. 技术架构建议

| 层 | 首版选择 | 用途 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 页面、移动端布局、交互和像素动效 |
| 后端 | Node.js + TypeScript + Fastify | 账号、房间 API、静态资源、权限校验 |
| 实时通信 | Socket.IO | 房间广播、提交答案、事件确认和重连 |
| 数据 | SQLite + 结构化题库 | 房主账号、历史战绩与结果持久化 |
| 对局运行 | 单进程内存状态机 | 按房间串行处理状态、计时与结算 |
| 部署 | Docker Compose | 应用与可选的 cloudflared 服务 |
| 接入 | Cloudflare Tunnel 优先评估 | 同域名 HTTPS 与 WebSocket，减少源站暴露 |

这是拟定技术路线，尚未安装依赖或固定版本。实施时选受支持稳定版本并提交锁文件。前端和 API 通过同域名提供，减少跨域和会话配置问题。初版无 Redis、无微服务。

数据库保存账号、对局摘要、逐题结果；正在运行的房间在内存中。每题结算持久化一次，完成对局时事务写入最终战绩。服务重启后将未完成记录标记为中断，避免展示为正常完成。

## 7. 服务端状态与通信契约

### 7.1 状态机

```text
LOBBY → QUESTION → REVEAL → QUESTION → … → FINISHED
                    └──────── Boss 击败或题数耗尽 ──────┘
QUESTION / REVEAL ↔ PAUSED
任意非关闭状态 → CLOSED（房主关闭或到期回收）
```

暂停需要保留原阶段和剩余时长。所有定时回调携带对局 ID、题目 ID 和阶段版本；旧计时器即使触发，也不能影响新题或新一局。

### 7.2 关键模型

- `Room`：内部 ID、邀请标识、房主 ID、设置、状态、版本、玩家、活跃对局、最后活动时间。
- `Player`：稳定游客 ID、昵称、头像、角色、在线连接、血量、连击、正确/错误/超时次数、伤害、待生效角色。
- `Match`：ID、开局名单、Boss 血量、题目序列、当前题索引、阶段、时间、结果。
- `Question`：ID、分类、难度、题干、选项、正确答案、解释；正确答案只保留在服务器直到结算。
- `Submission`：对局 ID、题目 ID、玩家 ID、选项 ID、服务端接收时间、请求 ID；数据库对前三项保证唯一。
- `RoomEvent`：递增序号、类型、服务端时间、可见性、事件数据；房主事件范围限制在当前游戏房间。

正确率 = 答对数 / 本人承担作答义务的题数；错误与超时均计入分母，观战题不计入。排行榜同时显示答对/应答题数，避免只看百分比误判。

### 7.3 HTTP 与实时事件草案

HTTP：`POST /api/host/login`、`POST /api/host/logout`、`GET /api/session`、`POST /api/rooms`、`GET /api/health`。退出会话和管理操作需做相应 CSRF/Origin 校验。

客户端事件：`room:join`、`player:set-role`、`match:start`、`answer:submit`、`match:pause`、`match:resume`、`match:restart`、`player:kick`、`room:lock`。

服务端事件：`room:snapshot`、`room:updated`、`question:started`、`player:submitted`、`question:resolved`、`match:paused`、`match:finished`、`room:closed`、`request:error`。

每次变更包含 `roomVersion`，题目相关请求包含 `matchId` 与 `questionId`。重复提交采用幂等确认，过期题目、观战身份、暂停状态、非法选项一律拒绝，不重复扣血。

Socket.IO 重连恢复只作为优化；失败后必须获取完整快照。稳定游客 ID 不能使用会变化的 socket ID。同一身份多开标签页时，只允许一个连接成为答题控制端，其余显示只读状态。

## 8. 题库与基础安全

- 初版准备约 60–100 道经过检查的四选一题，每题唯一正确答案和一句解释，单局不重复。
- 题型侧重生活常识、轻逻辑、趣味知识，避开时效性强、容易争议或需要复杂计算的题目。
- 正确答案不能出现在作答阶段网络载荷、静态前端资源、二维码或客户端题库中。
- 登录、邀请码尝试和答题消息按身份与连接限流；服务器验证消息结构、字段长度、房间成员资格。
- 昵称按文本渲染，避免 HTML 注入；不因公网开放而暴露管理接口或数据库。
- 日志不记录明文密码、完整会话、私钥或 Cloudflare Token。
- 真实源站、跳板连接信息保存在 `local/`，不进入公开仓库和前端包。

## 9. 开发顺序

| 阶段 | 产出 | 完成标准 |
| --- | --- | --- |
| P0 需求与网络入口 | 本文档、管理链路与 DNS 方案 | 确认 Windows 接入方式，验证目标域名的双端长连接 |
| P1 游戏闭环 | 工程骨架、服务端状态机、单 Boss、少量题目 | 本地两个浏览器能建房、入房、完成一局 |
| P2 完整房间 | 房主账号、二维码、身份恢复、观战切换、排名 | 6 个玩家身份与房主视角工作正常 |
| P3 视觉与题库 | 移动端像素界面、动效、音效开关、精选题库 | 真机答题易读、按钮好点、节奏流畅 |
| P4 部署与联调 | 镜像、Compose、DNS/隧道、备份与回滚说明 | 大陆手机可进房、答题、重连；源站不被网页直接引用 |
| P5 试玩调整 | 数值、题目与体验修正 | 5–6 人完成多局，修复阻断性问题 |

## 10. 验收与验证重点

1. 二维码实际打开目标域名，游客无注册即可进入，满员与房间失效有清晰提示。
2. 六个参战客户端看到一致题目、Boss 血量和结算榜；房间之间不串消息。
3. 全员提前提交后提前结算；无人提交到期也结算；每题恰好结算一次。
4. 同一题重复点击、重发消息、并发提交均只产生一次结果，过期答案不生效。
5. 参与/观战切换不改变本题义务、不回血；房主无提前答案优势。
6. 暂停、恢复、重开、掉线与旧定时器不会导致重复题目或重复伤害。
7. 重连与刷新后恢复自己的提交和血量；观战用户不能调用答题或管理接口。
8. 在大陆至少两种网络下实测连接、连续答题与切换网络；记录断线、延迟和恢复结果，不能仅凭首页能打开判定通过。
9. 检查前端包、初始题目响应和邀请链接不含答案、源站地址或认证秘密。
10. 对房间状态机、截止时间、重复提交、权限和计分做针对性测试；用浏览器多上下文做关键流程联调。低影响样式变更以真机查看为主。
